# Лабораторная работа №2
## Реляционная модель и SQL для проекта «Образования.нет»

### 1. Основание для проектирования

Модель построена на концептуальной ER-модели из лабораторной работы №1. В ней выделены сущности User, Role, Course, Module, Lesson, Enrollment, LessonProgress, Assignment, Submission, Quiz, Question, Attempt и Answer, а также связующая сущность UserRole. Основные связи: пользователь имеет роли; преподаватель создаёт курсы; курс содержит модули; модуль содержит уроки; пользователь записывается на курс через Enrollment; для обучения фиксируется прогресс; курс содержит задания и тесты; тест содержит вопросы; попытка содержит ответы.

Дополнительно в первой работе зафиксировано изменение требования: курс может иметь курсы-пререквизиты; нельзя записаться на курс до завершения обязательных пререквизитов; самозависимость и циклические зависимости запрещены. Это вынесено в отдельную миграцию 002.

### 2. Логическая модель PostgreSQL

| Таблица | Назначение | Первичный ключ | Основные внешние ключи |
|---|---|---|---|
| roles | Справочник ролей | id | — |
| users | Учётные записи | id | — |
| user_roles | Пользователи и роли | (user_id, role_id) | users, roles |
| courses | Учебные курсы | id | users(teacher_id) |
| modules | Модули курса | id | courses |
| lessons | Уроки | id | modules |
| enrollments | Записи пользователя на курс | id | users, courses |
| lesson_progress | Прогресс по урокам | (enrollment_id, lesson_id) | enrollments, lessons |
| assignments | Практические задания | id | courses |
| submissions | Сдачи заданий | id | assignments, enrollments, users(reviewer_id) |
| quizzes | Тесты | id | courses |
| questions | Вопросы тестов | id | quizzes |
| question_options | Варианты ответа | id | questions |
| attempts | Попытки прохождения теста | id | quizzes, enrollments |
| answers | Ответы внутри попытки | (attempt_id, question_id) | attempts, questions/options |
| course_prerequisites | Связь курс → пререквизит | (course_id, prerequisite_course_id) | courses, courses |

Кардинальности: User 1:N Enrollment, Course 1:N Enrollment, Course 1:N Module, Module 1:N Lesson, Enrollment 1:N LessonProgress, Course 1:N Assignment, Assignment 1:N Submission, Course 1:N Quiz, Quiz 1:N Question, Question 1:N QuestionOption, Quiz 1:N Attempt, Attempt 1:N Answer. Связь User↔Role является M:N через UserRole. Связь «курс-пререквизит» также M:N через CoursePrerequisites.

### 3. Нормализация до 3НФ

Схема приведена к третьей нормальной форме:

1. Каждая таблица описывает одну предметную сущность или одну связь M:N.
2. Нет повторяющихся групп и многозначных полей: роли, варианты ответов и ответы вынесены в отдельные таблицы.
3. Неключевые атрибуты зависят от ключа, а не от другого неключевого атрибута. Например, данные преподавателя не дублируются в Course, а определяются через teacher_id → Users.
4. Составной ключ LessonProgress означает конкретную пару «запись на курс + урок», поэтому один и тот же урок не дублируется внутри одной записи.
5. Answer не хранит текст варианта ответа повторно; выбранный вариант определяется через option_id.

Намеренной денормализации для PostgreSQL не используется. Итоговый прогресс курса, факт прохождения теста и возможность завершения курса рассчитываются из исходных данных. Это уменьшает риск рассинхронизации итоговых полей.

### 4. Ключи: суррогатные и естественные

Для основных сущностей используются суррогатные ключи BIGINT GENERATED ALWAYS AS IDENTITY: users.id, courses.id, modules.id, lessons.id, assignments.id, submissions.id, quizzes.id, questions.id, question_options.id, attempts.id и др.

Причина: бизнес-значения могут меняться, иметь разные форматы или быть длинными. Например, email является уникальным бизнес-атрибутом пользователя, но не используется как PK.

Естественные ограничения сохранены как UNIQUE: users.email, roles.code, (teacher_id, title) для курса, позиции элементов внутри родителя и составные идентификаторы связей.

### 5. Ограничения целостности

Используются:

- `NOT NULL` для обязательных атрибутов;
- `UNIQUE` для email, кодов ролей, позиций и повторных бизнес-операций;
- `CHECK` для статусов, числовых диапазонов, положительных позиций и количества попыток;
- `FOREIGN KEY` для ссылочной целостности;
- `IDENTITY` для генерации идентификаторов;
- частичный уникальный индекс для ограничения одной активной попытки теста;
- триггеры для правил, зависящих от нескольких таблиц: роль преподавателя курса, доступность опубликованного курса, соответствие урока записи, соответствие задания записи, роль проверяющего, лимит попыток, отсутствие циклов пререквизитов.

### 6. Миграции

`001_initial_schema.sql` создаёт основную схему с нуля.

`002_course_prerequisites.sql` безопасно добавляет новую функциональность — таблицу курсов-пререквизитов и проверку циклов.

Таким образом, обновление выполняется последовательно, а не изменением уже применённого файла.

### 7. Тестовые данные

Файл `data/seed.sql` содержит согласованный набор:

- 4 пользователя;
- роли student/teacher/moderator/admin;
- 3 курса с разными статусами;
- 1 связь-пререквизит;
- модули и уроки;
- задание и сдачу с результатом;
- тест, вопросы и варианты ответов;
- завершённую попытку теста и ответы;
- запись обучающегося и прогресс уроков.

### 8. Сценарии жизненного цикла

`scenarios/lifecycle.sql` демонстрирует:

1. User: регистрация пользователя → автоматическое назначение роли student.
2. Course: Draft → Moderation → Published → Archived.
3. Enrollment: Active → Completed.
4. Submission: Created → On Review → Accepted.
5. Attempt: Active → Completed.

Таким образом, механический CRUD для всех таблиц не используется; показаны реальные бизнес-сценарии платформы.

### 9. Негативные тесты

`tests/negative_constraints.sql` проверяет как минимум семь ограничений:

1. повторный email → UNIQUE;
2. NULL в full_name → NOT NULL;
3. недопустимый статус курса → CHECK;
4. position = 0 у Module → CHECK;
5. несуществующий user_id → FOREIGN KEY;
6. повторная запись на один курс → UNIQUE;
7. вариант ответа от другого вопроса → составной FOREIGN KEY/триггер.

### 10. Автоматизированная проверка

`scripts/test_all.sh` выполняет два режима:

- чистая установка: создать пустую БД → применить 001 → 002 → seed → негативные тесты;
- проверка обновления: создать БД на версии 001 → применить 002 → seed → проверить результат.

Это закрывает вариант «Восхитительно»: автоматическая проверка всех миграций на чистой базе и обновление с предыдущей версии.

### 11. Вывод

В результате концептуальная модель «Образования.нет» переведена в нормализованную реляционную модель PostgreSQL. Для таблиц определены типы данных, PK/FK, обязательность полей, уникальность и проверки диапазонов. Добавлены версионируемые миграции, тестовые данные, сценарии жизненного цикла и негативные проверки. Отдельной миграцией реализована поддержка курсов-пререквизитов из изменённого требования первой лабораторной работы.
